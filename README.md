# Mempool Hysteresis: simulator and SARA recovery-audit framework

Working model for CBS3015 (Information Systems Audit and Control), Digital Assignment 3, Phases 1–4 of the
implementation plan. It answers two questions with a discrete-event blockchain simulation:

1. **Does a transient network disturbance leave residual state behind after connectivity returns?**
   (mempool *residue*: transactions some nodes hold pending while others have never seen them, and
   *backlog debt*: extra pending work relative to an undisturbed history)
2. **Can a state-aware audit framework (SARA) certify recovery more accurately than connectivity-based
   recovery assessment?** Compared against two baselines and three ablations.

Everything is synthetic and stated as such. Every number used in the paper comes from
`results/numbers.json`, which is generated by code from the stored runs.

## Quick start

```bash
pip install numpy scipy pandas matplotlib networkx pytest   # Python 3.11+
pip install streamlit plotly                                # only for the frontend (streamlit run app.py)
python -m pytest -q tests/                                  # unit, regression and frontend tests (48, ~2 min)
python demo.py --dist partition --seed 1000                 # replay one disturbance under B1, B2, SARA
python demo.py --dist all                                    # one line per disturbance type
```

`demo.py` prints each policy's audit trail (alarms, risk tiers, reconciliation rounds, recovery
declarations) and a table of what each policy *believed* versus what was *true*, and saves a plot to
`results/demo_<dist>_<seed>.png`.

## Extensions (separate from the main study)

Three extension experiments are reported separately in `results/extensions/EXTENSIONS.md`: pre-registered
definitions, hypotheses, seeds and configurations (hash-checked), a change log, generated results tables and the
limitations. **The main study is unchanged.** Every new model feature is off by default, and with the defaults every
run is bit-for-bit identical to the runs behind `results/numbers.json`: `tests/test_regression.py` replays a
snapshot of 40 runs (seeds 1000–1001, all disturbances, B1/B2/SARA, clean histories) recorded before any code was
edited. SARA keeps its pre-specified calibrated values throughout; a re-calibrated SARA appears only in B, labelled
as a secondary result.

| Extension | Question | Model change (off by default) | Seeds |
| --- | --- | --- | --- |
| A. Confirmation delay and block composition | Do residue and backlog debt delay users? Does a policy that certifies recovery falsely also leave users worse off? | none; new metrics in `mh/ext_metrics.py` | the main study's own runs (1000–1199, re-simulated and checked identical to `all_runs.csv`) + replication 3000–3099 |
| B. Scale and topology | Do the findings hold with 20 and 50 nodes, degree 8, Erdős–Rényi and Watts–Strogatz graphs? | `SimConfig.topology` (default `random_regular`) | 3000–3029 per cell |
| C. Bounded mempools and eviction | Can eviction leave divergence that neither gossip nor SARA can repair? | `SimConfig.mempool_cap` (default `None`) | 3000–3099 |

## Frontend

A local Streamlit app runs the real simulator from the browser and shows the stored results. It only imports `mh/`
and reads `results/`; it never changes either.

```bash
pip install streamlit plotly          # tested with streamlit 1.60 and plotly 6.9
streamlit run app.py                  # from the project root; opens http://localhost:8501
```

| Page | What it does |
| --- | --- |
| Overview | Project summary, study settings, status of the stored result files |
| Simulator | One disturbance under one policy, live: verdict, metric cards (the values `demo.py` prints), true state vs what the policy reported and watched, confirmation delay against the paired clean run (extension A metrics), evictions and evicted-divergence when a mempool cap is set (extension C), audit trail |
| Policy comparison | B1, B2 and SARA on the same seed: the believed-vs-true table, generated verdicts, overlaid truth, user delay, side-by-side audit trails, and all six disturbances for the seed |
| Network replay | The nodes and links over time (slider or animation): share of pending transactions per node, true link state, the monitor's view, residue, block, reorg, policy and eviction events, per-node evicted and rejected transactions when a cap is set |
| Study results | Main study (numbers.json, sweeps.json, verification.json, figures, RESULTS.md) and, separately, the extensions (ext_numbers.json, EXTENSIONS.md, figures); every table names its source key and downloads as CSV |
| Method | Model, ground truth, policies, statistics, calibration, the extension definitions and the limitations, read from this README, `experiments/analyze.py` and `results/extensions/EXTENSIONS.md` |

The sidebar starts from the study settings (seed 1000, calibrated configuration): disturbance, seed, topology, node
count, degree, transaction rate (optionally holding block-space utilisation, as extension B does), mempool capacity
(off by default; the extension C levels are offered) and the disturbance parameters. Changes apply to a copy of the
configuration, and any run that differs from the study settings is labelled "exploratory, not part of the study".
Settings can also be given in the link, e.g. `http://localhost:8501/Simulator?dist=loss&seed=1002&cap=loose&policy=SARA`.
`tests/test_app_lib.py` checks that the app's numbers equal `demo.py`, `results/verification.json` and the stored
extension runs, and that the replay's residue equals the evaluator's.

### Playback and themes

After each new run (Apply, or a new disturbance, seed or policy) the Simulator, Policy comparison and Network replay
pages play the stored result back over about four seconds. The charts draw in from left to right behind a "now"
cursor, and the metric cards, verdicts, believed-vs-true table and audit trails show "pending" until the playback
reaches the event they describe. Playback is display only: the run is computed (or read from the cache) first, every
frame shows the stored series up to the playback time, and the last frame is the static result.

- **Controls** (one row above the results): Play/Pause, Replay (from the start), Skip to end, speed 0.5× / 1× / 2× /
  4×, and "Show results instantly", which skips the playback after new runs for the rest of the session. On Network
  replay the time slider advances by itself; Pause hands it back to you. Other clicks (tabs, downloads, a theme
  change) never restart a playback.
- **Static pages** for screenshots: add `static=1` to the link, e.g.
  `http://localhost:8501/Simulator?dist=partition&seed=1000&static=1`. The page renders the final state at once,
  without controls. Network replay then opens at +10 s, as before.
- **Themes**: dark is the default. Switch with the menu at the top right (⋮, then System / Light / Dark); the choice
  is remembered by the browser for every page. For light-theme screenshots choose Light, then open the static links.
  Colours live in `.streamlit/config.toml` (app), `app_lib/palette.py` (charts: B1 red, B2 amber, SARA blue, with a
  brighter step of each for the dark theme) and `app_lib/style.py` (rounded corners).

`tests/test_playback.py` checks the playback helpers: values stay pending until their event, and the last frame
shows exactly `demo.py`'s values.

## What is modelled

- **Network**: 10 nodes on a random 4-regular topology, 20–120 ms links, inv/getdata/tx relay with a
  1 s trickle, TCP transport (loss delays messages through retransmission backoff, blackholed directions
  buffer). Partitions and isolations reset connections, and peers reconnect afterwards.
- **Blocks**: Nakamoto-style Poisson mining (mean 15 s), fee-priority blocks of 80 transactions
  (utilisation 0.75), longest-chain fork choice, reorgs return transactions to the mempool.
- **Residue mechanisms**: no mempool exchange on reconnect (Bitcoin Core default), reorg-returned
  transactions not re-announced, a miner can only include transactions it holds.
- **Disturbances**: partition, node isolation, packet loss, latency spike, asymmetric link, transaction burst.
- **Common random numbers**: workload, mining schedule, topology and per-message network luck are fixed by
  the seed, so a clean and a disturbed history differ only in the disturbance.

## Policies

| Policy | Sees | Does | Declares recovery when |
| --- | --- | --- | --- |
| B1 connectivity-only | link probes | nothing | every link is healthy again |
| B2 protocol resync | link probes | full pending-hash exchange + chain sync on every (re)connection (geth-style) | links healthy and every resync delivered |
| SARA (proposed) | link probes + node state (mempool mirror, tips) | tiered, targeted pull reconciliation of missing transactions | links healthy, risk tier LOW for 5 audits, tips on one chain |
| SARA −D | as SARA, but mempool *sizes* instead of set divergence | full exchange for flagged nodes | size proxy LOW for 5 audits |
| SARA −R | as SARA, without risk tiers or backlog | pull on any divergence | divergence exactly zero for 5 audits |
| SARA −V | as SARA, without the verification loop | one reconciliation round | immediately after that round |

The ablation is one class with three toggles: `SARA(use_divergence, use_risk, use_verification)`.

## Ground truth (never visible to any policy)

- **Residue** `Res(t)`: mature transactions created before the disturbance ended that some node has
  pending while another node has neither pending nor confirmed. Threshold-free; zero in every clean run.
- **Backlog debt**: pending-set size of the disturbed history minus the paired clean history, sampled at the
  same instants (same workload, same mining schedule).
- **False-recovery exposure (FRE)**: seconds after the disturbance ended during which a policy reported
  "recovered" while residue (FRE_state) or backlog debt (FRE_backlog) remained.

## Limitations to state in the paper

- Simulation only; the model's protocol behaviours are cited, not measured on live networks.
- SARA assumes an operator monitoring plane that can read every node's mempool, which fits an enterprise
  or consortium node fleet, not a public network the auditor does not operate.
- Backlog debt smaller than the natural variability of the mempool is invisible to any monitor without a
  counterfactual, so SARA's backlog check is an operating-envelope check, not a debt measurement.
